# Brand — the mark, the favicon, and the link-preview card

Written 2026-07-27, when the site got its first brand assets. Before that it shipped a
`description` meta and nothing else: blank browser tab, and every share of the URL rendered as a
bare text blob.

## The mark

A **brace pair enclosing a block**. maud's sigil is `html! { }`, so the braces *are* the library
and the block between them is what comes out.

It is typographic rather than illustrated, on purpose:

- It survives 16×16, which an illustration does not.
- It needs no asset pipeline — it is one hand-written SVG, drawn in the library's own tokens.
- It says "template macro" rather than "generic UI kit".

**There is deliberately no mascot.** This library's argument is rigor — the registration-parity
guards, two border tokens because 1.27:1 made unchecked checkboxes invisible, the WCAG 1.4.11
sweep. A mascot sells approachability and dilutes that. The peer set it is measured against
(shadcn/ui, Radix, Base UI) and the crates it sits beside (tokio, axum, maud) are wordmark-only.
A crab would be both derivative and, in 2026 dev tooling, the loudest AI-slop tell available.

Rejected alternative: an **M monogram**. A bare letterform is the most interchangeable mark
possible and tells a visitor nothing about what they are looking at.

## The files

| File | What it is | Regenerated by |
|---|---|---|
| `assets/favicon.svg` | The mark. Hand-edited; the source of truth. | — (edit directly) |
| `assets/og-source.html` | The 1200×630 link-preview card, as HTML. | — (edit directly) |
| `assets/og.png` | Rasterised card. **Committed** — crawlers fetch a URL, not a build step. | `bun run build:og` |
| `assets/apple-touch-icon.png` | 180×180 opaque tile, inlined from `favicon.svg`. | `bun run build:og` |

Served at the site root by three routes in `examples/showcase.rs`, and copied to `public/` by
`js/export-static.mjs`. They must sit at exactly those paths — `page_head()` and the absolute
`og:image` URL point at them.

```bash
bun run build:og     # after editing og-source.html or favicon.svg
bun run build:static # so public/ picks the new bytes up
```

## Three traps, all of which bit while building this

### 1. A double hyphen in an XML comment breaks the whole SVG, silently

The first draft documented the token names in full. `--mui-accent` inside an `<!-- -->` comment
is **illegal XML**: `--` may not appear inside a comment. The file stopped parsing entirely, every
browser rendered a broken-image glyph, and *nothing logged an error anywhere*.

Write token names without their leading dashes inside comments (`mui-accent`, not the full form).
`registration_parity::favicon_svg_is_parseable` now rejects it.

### 2. The favicon's artboard is padded; a lockup's must not be

`favicon.svg` uses a 32×32 artboard with the ink inset (paths span x 5..27, y 4..28). That padding
is correct for an icon — one that bleeds to the tile edge looks wrong — but it is **invisible
weight** in a lockup, and it makes the glyph impossible to size against type.

Using the padded artboard in the header drew 14.24px of ink beside an 11.27px cap height: 26%
oversized, overshooting the cap line by 2.25px, floating high.

The header copy in `page_header()` therefore uses a viewBox cropped to the ink —
`viewBox="3.5 2.5 25 27"` (the 3-wide round-capped stroke reaches 1.5 past each path end) — sized
at `0.75em` so it tracks the wordmark instead of being pinned to a fixed pixel size. With the box
equal to the ink, the header's existing `align-items: baseline` puts the ink bottom exactly on the
text baseline, and the ink rises ~0.7px above the cap line: the small overshoot round terminals
need to read level with flat-topped letters.

**If you re-draw the mark, re-derive that viewBox** — it is the ink's bounding box, not a constant.

### 3. Measuring a baseline with a Range gives you the LINE BOX, not the ink

While checking trap 2 I nearly shipped a `translateY(-0.1846em)` correction on top of an already
correct alignment. The measurement said it was needed. The measurement was wrong:

```js
// WRONG — a range rect reports the line box; this baseline is ~3px off.
range.selectNodeContents(el.firstChild);
const baseline = range.getBoundingClientRect().top + ctx.measureText(s).actualBoundingBoxAscent;

// RIGHT — a zero-width inline-block's bottom edge IS the baseline, by definition.
const probe = document.createElement('span');
probe.style.cssText = 'display:inline-block;width:0;height:0;vertical-align:baseline';
el.appendChild(probe);
const baseline = probe.getBoundingClientRect().bottom;
probe.remove();
```

Use the probe. A magic nudge calibrated against a bad reference looks right today and drifts the
moment the font or line-height changes.

## Colour follows the reader, two different ways

The mark is drawn in the accent pair: `#2563eb` (`mui-accent`, reads on white) and `#60a5fa`
(`mui-accent-text`, reads on near-black). How it picks between them differs by context, and the
difference is load-bearing:

- **`favicon.svg`** carries its own `@media (prefers-color-scheme: dark)` rule. A standalone file
  cannot read the site's CSS custom properties, so the OS preference is the only signal available.
- **The header mark is inlined** in `page_header()` and reads `var(--mui-accent-text)`. This site
  has an *explicit* theme toggle that does **not** follow the OS, so an `<img src="/favicon.svg">`
  would sit at the wrong tint whenever the two disagree.
- **`og-source.html`** pins `#60a5fa` as a literal. The card is rasterised once against a dark
  background, so it cannot read a live custom property — and stripping the `<style>` block when
  inlining the mark for `apple-touch-icon.png` is deliberate: otherwise the committed PNG would
  depend on the OS theme of whichever machine ran the build.

## The card bakes in a number

`assets/og-source.html` states the component count as text, and `og.png` rasterises it into
pixels — nothing can correct it at runtime. `registration_parity::og_card_component_count_matches_reality`
pins it against `COMPONENT_NAMES.len()`, and also checks the PNG is exactly 1200×630 (a size
mismatch downgrades some crawlers to a card with no image at all).

Add a component → the test fails → update the card and `bun run build:og`.
